# Spec: M6 - the Kubernetes estate on kind: `nordwind-bank` Helm chart (three services), kube-prometheus-stack, PrometheusRules, Alertmanager route B to the forwarder, `task estate-up`, chaos via ConfigMap, `estate-demo.yml` v1

Builds on M2 (`services/ingest/adapters/alertmanager.py` accepts Alertmanager webhook payloads; label `service` names the service, `severity` maps critical/high/warning to sev1/2/3, receiver names containing `kafka` mark route A - everything in M6 is route B), M5 (`bank/azure/alert_forwarder` accepts Alertmanager webhooks at its function URL and forwards them signed to ingest), M4 (fault modes as a pattern; here the control plane is a Kubernetes ConfigMap, not DynamoDB), `docs/DESIGN.md` section 4.4 (D6/D7: kind, not a cloud cluster). Repository conventions unchanged; all offline gates must pass. New CI gates for this milestone: `helm lint`, `helm template | kubeconform -strict` (Kubernetes 1.31 schemas), and `pytest` for the service code. Nothing in this milestone costs money: kind on the laptop or on a GitHub-hosted runner; Kafka comes in M7 (leave the topic/producer hooks as no-ops behind a `kafka.enabled=false` value).

## Requirements

1. Services, `bank/k8s/<service>/` for `cards_authorization`, `fraud_scoring`, `open_banking_api`: one small Python 3.12 HTTP app each (standard library `http.server`; `prometheus_client` is the one new dependency), listening on 8080 with `/healthz`, `/metrics`, and a `/work` endpoint hit by an in-process ticker every second so metrics move without external load. Fault mode is read from the file `/etc/nordwind/fault` mounted from the ConfigMap, re-read every 5 s, empty = normal:
   - cards-authorization: histogram `cards_auth_request_seconds`, counter `cards_auth_requests_total{result="ok|error"}`; faults `timeouts` (observe 3.0 s latencies) and `issuer-down` (every request `result="error"`).
   - fraud-scoring: histogram `fraud_score_bucket` (scores drawn around 0.2 normally), counter `fraud_scored_total`; faults `model-drift` (scores drawn around 0.8), `latency` (2 s observations), `crashloop` (exit 1 after 10 s, so the Deployment restart policy produces CrashLoopBackOff); `lag` is M7 (accepted but a no-op now).
   - open-banking-api: counter `openbanking_responses_total{code="200|429"}`, gauge `openbanking_cert_expiry_seconds` (default 90 days ahead); faults `rate-limit-storm` (80 % of responses `429`) and `cert-expiry` (gauge set to 3 days ahead).
   One shared module `bank/k8s/_shared/` (fault file reader, ticker, metrics server). One `Dockerfile` per service (python:3.12-slim, non-root, `HEALTHCHECK`), built by `task estate-up` and by `estate-demo.yml` and loaded into kind with `kind load docker-image` - no registry needed.
2. Helm chart `deploy/helm/nordwind-bank/` (apiVersion v2): one Deployment + Service + ServiceMonitor per service (labels `app.kubernetes.io/name`, `app.kubernetes.io/part-of: nordwind-bank`, `nordwind.dev/c4-container: <service>`), resource requests/limits, liveness/readiness on `/healthz`, `securityContext` (runAsNonRoot, readOnlyRootFilesystem, drop ALL), a ConfigMap `nordwind-faults` with one key per service (empty by default) mounted at `/etc/nordwind`, and a `PrometheusRule` with these rules (labels `service=<name>`, `severity`, annotations `summary`, `description`):
   `CardsAuthHighLatency` (p99 of `cards_auth_request_seconds` > 1 s for 2 m, high), `CardsAuthErrorRatio` (error ratio > 0.5 for 2 m, critical), `FraudScoreDrift` (mean score > 0.6 for 3 m, high), `FraudScoringCrashLoop` (`kube_pod_container_status_restarts_total` increase > 2 in 10 m, high), `OpenBankingRateLimitStorm` (429 ratio > 0.5 for 2 m, warning), `OpenBankingCertExpiringSoon` (`openbanking_cert_expiry_seconds` < 14 d, warning). `for` durations are short on purpose: the demo must reach a verdict in under 10 minutes.
3. Monitoring: `deploy/helm/values/kube-prometheus-stack.yaml` for the upstream `kube-prometheus-stack` chart (pinned version; Grafana disabled, Alertmanager enabled, 15 s scrape interval, `ruleSelectorNilUsesHelmValues: false`, `serviceMonitorSelectorNilUsesHelmValues: false`). Alertmanager config (a Secret `alertmanager-nordwind` rendered by the chart from values) with `group_wait: 10s`, `group_interval: 30s`, `repeat_interval: 1h`, receiver `route-b-forwarder` = `webhook_configs` with `url` from value `forwarder.url` (the Azure function URL including its `code=` query string) and `send_resolved: true`; if `forwarder.url` is empty the receiver is a null receiver and `helm lint` still passes.
4. `deploy/kind/cluster.yaml` (one control-plane node, Kubernetes 1.31 node image, `extraPortMappings` for 9090 and 9093 so `localhost:9090` / `localhost:9093` reach Prometheus/Alertmanager). `Taskfile.yml` tasks: `estate-up` (kind create if missing, helm repo add/update, install kube-prometheus-stack from the pinned version into `monitoring`, build the three images, `kind load`, `helm upgrade --install nordwind-bank` into `bank` with `--set forwarder.url=$FORWARDER_URL`, wait for rollout, print the UIs), `estate-down`, `estate-status` (pods + firing alerts from the Alertmanager API), `chaos-k8s -- <service> <mode>` (patch the ConfigMap key; `clear` empties it), `helm-lint`, `helm-template-check` (kubeconform).
5. `.github/workflows/estate-demo.yml` (`workflow_dispatch` + weekly schedule Sunday 06:00 UTC, single job, ubuntu-latest, 25-minute timeout): checkout, install kind/helm/kubeconform (pinned), `task estate-up` with `FORWARDER_URL` from the `demo` environment secret, then `python scripts/estate_scenarios.py --scenario cards-timeouts` which sets the fault, waits until Alertmanager shows `CardsAuthHighLatency` firing (poll `localhost:9093/api/v2/alerts`, 8-minute budget), then polls the console API (`CONSOLE_TOKEN` from the demo environment) until an alert with `estate=kubernetes` and `service=cards-authorization` has a verdict (10-minute budget) and prints it. Always: upload Alertmanager alerts JSON, Prometheus rules state and the three pod logs as artifacts, then `task estate-down`. The job fails if either wait times out. Concurrency group `estate-demo`, cancel-in-progress false.
6. `ci.yml` gains a `helm` job (helm lint + kubeconform on the rendered chart with default values and with `forwarder.url` set) and the k8s services join the normal `pytest` job. Trivy config scan on the rendered manifests (`trivy config`) with no HIGH/CRITICAL.
7. `cli/bankops`: `chaos` learns `--estate kubernetes`, which shells out to `kubectl patch configmap nordwind-faults -n bank` (documented; kubectl is monkeypatched in tests). `bankops tail` already shows estate.
8. Tests: `tests/bank/k8s/` - fault file reader (missing file, unknown mode, hot reload), each service's metric behaviour per fault using `prometheus_client` registries (no network), the crashloop exit path (monkeypatch `sys.exit`), `scripts/estate_scenarios.py` polling logic with HTTP monkeypatched (success, Alertmanager timeout, console timeout). Chart tests: a `helm template` golden test for the PrometheusRule (rule names and `service` labels present) run through `subprocess` and skipped when `helm` is not on PATH (CI has it).
9. Docs and diagrams: `docs/c4/workspace.dsl` - the `kubernetesEstate` software system gains containers `cards-authorization`, `fraud-scoring`, `open-banking-api`, `prometheus`, `alertmanager` and the deployment view `kind` (laptop / GitHub Actions); route B relationship `alertmanager -> forwarder "webhook"`; regenerate. `docs/runbooks/kubernetes-estate.md`: laptop quick start (Docker Desktop memory note ~6 GB), the UIs, the chaos cookbook for the six rules with expected time-to-verdict (~6-9 min), how to read the `estate-demo` artifacts. `docs/DESIGN.md` section 3: the three Kubernetes services marked deployed by M6 (M7 adds Kafka). README roadmap row M6.

## Non-requirements

Kafka/Strimzi, `alerts-bridge`, `kafka-relay`, kafka-exporter and route A (M7); Grafana; AKS; Ingress/TLS inside the cluster; any live cluster in `pytest` (the CI `helm` job and `estate-demo.yml` are the live gates).
