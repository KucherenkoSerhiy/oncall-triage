# Spec: M5 - the Azure estate: customer-notifications Function, Azure Monitor alerts, the always-on alert forwarder, `bankops chaos` for Azure

Builds on M2 (`services/ingest` already has the `azure-monitor` adapter for the *common alert schema* and HMAC verification), M2b (`cli/bankops`, console API), M4 (the fault-control pattern: a DynamoDB `bank-faults` item per service, set through `POST /chaos/{service}`), and the Azure bootstrap (`infra/bootstrap/azure`: resource group `rg-nordwind-triage-demo`, deploy identity = Contributor on that group; `infra/azure` root applied by `deploy.yml` with `ARM_*` OIDC variables). Repository conventions unchanged; all offline gates must pass (Python: ruff / ruff format / mypy / pytest; Terraform: fmt, `init -backend=false` + validate, tflint with the azurerm ruleset, checkov with inline reasons). Azure is budgeted at $2/month: Functions on the Consumption plan, one Storage account (LRS), Application Insights with the workspace's free 5 GB and sampling on, at most 3 alert rules. No Key Vault yet unless a secret truly needs it (see 5).

## Requirements

1. `bank/azure/customer_notifications/` - an Azure Functions (Python v2 programming model, `function_app.py`) app with a timer trigger every minute that "sends" 20 notifications and emits two custom metrics through OpenTelemetry/Application Insights: `notifications_sent` and `provider_429`. Faults come from the same control plane as M4 but Azure cannot read the AWS table, so the app polls `GET https://api.triage.serhiykucherenko.dev/chaos` (bearer token from app setting `CONSOLE_TOKEN`) at most once per minute and caches the answer: `provider-429` -> emit `provider_429 = 20` and raise `RuntimeError("SMS provider returned 429 Too Many Requests")` (drives the Function `Failures` metric); `backlog` -> emit `notifications_backlog = 150` and succeed. Add `customer-notifications` to the valid services in the console API's chaos route and to `bankops chaos`.
2. `bank/azure/alert_forwarder/` - a second Function app (HTTP trigger, function-key auth) that accepts (a) Azure Monitor **common alert schema** payloads from an action group and (b) Alertmanager webhook payloads (route B, M6), normalises nothing itself, and forwards the raw payload to the ingest API as `{"source": "azure-monitor" | "alertmanager", "payload": ...}` signed with HMAC (`X-Nordwind-Timestamp`, `X-Nordwind-Signature`; secret from app setting `INGEST_HMAC_SECRET`; same algorithm as `services/ingest/hmac_auth.py`, re-implemented in the function with a shared test vector so the two never drift). It distinguishes the two payload shapes by the presence of `data.essentials` (Azure) versus `alerts` (Alertmanager). Returns 202 on success, 502 with the ingest status on failure; logs one JSON line per forward (`source`, `ingest_status`, `alert_count`).
3. Shared code: `bank/azure/_shared/hmac_sign.py` (sign only) with a unit test asserting a fixed secret/timestamp/body produces the exact signature `services/ingest/hmac_auth.sign` produces (import both in the test); do not import `services.ingest` from the function apps themselves (they deploy alone).
4. Terraform, `infra/azure`: Storage account (`nordwindtriagedemo<suffix>`, LRS, TLS 1.2, no public blob access), Log Analytics workspace (PerGB2018, 30-day retention, daily cap 0.2 GB) + Application Insights (workspace-based, sampling 20 %), a Linux Consumption service plan (Y1), two `azurerm_linux_function_app`s (Python 3.12, system-assigned identity, app settings: `APPLICATIONINSIGHTS_CONNECTION_STRING`, `CONSOLE_TOKEN`, `INGEST_HMAC_SECRET`, `INGEST_URL` = `https://api.triage.serhiykucherenko.dev/alerts`, `CHAOS_URL`), an action group `nordwind-triage-demo-alerts` with a webhook receiver pointing at the forwarder's function URL (common alert schema **enabled**), and three alert rules that fire into it: metric alert on the notifications app `FunctionExecutionCount`-based failures (`Failures` >= 3 over 5 min, severity 2), a log alert (scheduled query) on the custom metric `provider_429` (sum >= 20 over 5 min, severity 2), and a metric alert on `notifications_backlog` >= 100 (severity 3). Alert rule names `nordwind-triage-demo-customer-notifications-<Signal>-Sev<N>`; descriptions start with `service=customer-notifications`. Tags `c4_container` = `notifications` / `forwarder` / `monitor` on every resource that supports tags.
5. Secrets on Azure: `infra/azure` must not depend on AWS resources, so `CONSOLE_TOKEN` and `INGEST_HMAC_SECRET` are not read from SSM inside Terraform. Instead `infra/aws` already outputs the two parameter names and `deploy.yml`'s Azure plan/apply step reads the two SSM values with the AWS role (same pattern as the smoke step) and passes them as `-var="console_token=..." -var="ingest_hmac_secret=..."` (variables marked `sensitive`). Document the trade-off in `infra/README.md`: app settings are plaintext in the Function configuration (visible to Contributors of the group) - the accepted v1 posture, mirroring the Lambda environment on AWS; Key Vault references are the M9 upgrade.
6. Function code deployment: zip deploy through Terraform (`zip_deploy_file` on the function app, built by `archive_file` from each `bank/azure/<app>/` directory including `requirements.txt` and `host.json`); document that the first deploy takes ~3 minutes to warm.
7. `deploy.yml`: the Azure plan/apply steps get the two variables from step 5; `terraform plan` for `infra/azure` must succeed on pull requests too (the PR job has the AWS role, so it can read SSM).
8. `cli/bankops`: `chaos customer-notifications --mode provider-429|backlog` works through the same console route; `bankops tail` shows `estate` as a column.
9. Tests: `tests/bank/azure/` - the notifications timer logic with the chaos poll monkeypatched (both faults + normal), caching of the chaos poll, the forwarder's shape detection and forwarding (HTTP monkeypatched; assert the HMAC headers verify with `services.ingest.hmac_auth.verify` against the test secret), the shared-sign test vector; console API accepts the new service; Terraform gates on `infra/azure`.
10. Docs and diagrams: `docs/c4/workspace.dsl` already models `azureEstate` (notifications, monitor, forwarder) - add the chaos-poll relationship (`notifications -> triage.api "GET /chaos"`) and the Application Insights container if it is missing; regenerate. `infra/README.md`: "What infra/azure deploys", the chaos cookbook entry for Azure (expected time-to-verdict 5-7 min: Azure Monitor evaluates every minute with a 5-minute window), and the function-key note. `docs/DESIGN.md` §3: customer-notifications marked deployed by M5.

## Non-requirements

Kubernetes / Alertmanager on the sending side (M6 supplies route B traffic to the forwarder), Key Vault (M9), Azure Front Door, custom domains on Azure, Azure DevOps, any live Azure call in tests.
