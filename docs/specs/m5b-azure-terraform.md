# Spec: M5b - infra/azure: Functions, Application Insights, action group, three alert rules; deploy.yml passes the two SSM secrets as sensitive variables

Slice 2 of 2 of `docs/specs/m5-azure-estate.md`. Builds on M5a (`bank/azure/customer_notifications`, `bank/azure/alert_forwarder`, `bank/azure/_shared`), M1 (`infra/azure` root today holds only the consumption budget; backend + `ARM_*` OIDC variables come from `deploy.yml`; `infra/bootstrap/azure` created resource group `rg-nordwind-triage-demo` in `westeurope` and gave the deploy identity Contributor on it), M2c (`infra/aws` outputs `console_token_parameter` and `hmac_secret_parameter`; the smoke job already reads both from SSM). Repository conventions unchanged; Terraform gates: `terraform fmt`, `init -backend=false` + `validate`, `tflint` (azurerm ruleset), `checkov` with an inline reason for any skip. Budget: Azure total <= $2/month - Consumption plan only, LRS storage, Log Analytics daily cap, sampling on, three alert rules.

## Requirements

1. `infra/azure` gains (all tagged `c4_container` = `notifications` / `forwarder` / `monitor` where tags are supported, plus the existing common tags): `azurerm_storage_account` (`nordwindtriage<random 6>`, Standard LRS, TLS 1.2 minimum, `allow_nested_items_to_be_public = false`, shared access keys enabled - Functions on Y1 need them; document), `azurerm_log_analytics_workspace` (PerGB2018, 30 days, `daily_quota_gb = 0.2`), `azurerm_application_insights` (workspace-based, `sampling_percentage = 20`), `azurerm_service_plan` (Linux, `Y1`), two `azurerm_linux_function_app`s named `nordwind-triage-demo-notifications` and `nordwind-triage-demo-forwarder` (Python 3.12, `https_only`, system-assigned identity, `site_config { application_insights_connection_string, ftps_state = "Disabled", minimum_tls_version = "1.2" }`, `zip_deploy_file` from an `archive_file` per app that packages `bank/azure/<app>/` plus `bank/azure/_shared/` at the zip root, `WEBSITE_RUN_FROM_PACKAGE = "1"`, `SCM_DO_BUILD_DURING_DEPLOYMENT = "true"` so `requirements.txt` is installed by Oryx). App settings: notifications - `CHAOS_URL`, `CONSOLE_TOKEN` (var, sensitive); forwarder - `INGEST_URL`, `INGEST_HMAC_SECRET` (var, sensitive). Variables `console_token` and `ingest_hmac_secret` are `sensitive = true` with no default.
2. Alerting: `azurerm_monitor_action_group` `nordwind-triage-demo-alerts` (short name `nwtriage`) with one `webhook_receiver` pointing at the forwarder's function URL including its default function key (`data.azurerm_function_app_host_keys` on the forwarder app; `use_common_alert_schema = true`). Three rules that target the notifications app and fire into the group, named `nordwind-triage-demo-customer-notifications-<Signal>-Sev<N>` with descriptions starting `service=customer-notifications`: `azurerm_monitor_metric_alert` scoped to the Application Insights component on metric `exceptions/count` (timer failures surface as exceptions; `Http5xx` on the site would miss them) with `Total >= 3` over `PT5M`, frequency `PT1M`, severity 2, signal name `Failures`; `azurerm_monitor_scheduled_query_rules_alert_v2` (KQL over the workspace: `customMetrics | where name == "provider_429" | summarize sum(value)` with threshold >= 20, window PT5M, evaluation PT1M, severity 2, signal `Provider429`); `azurerm_monitor_scheduled_query_rules_alert_v2` on `notifications_backlog` max >= 100 (severity 3, signal `Backlog`). Set `auto_mitigation_enabled = true` on the log rules so resolved notifications flow too.
3. `deploy.yml`: the `plan` and `apply` steps for `matrix.root == 'azure'` first read the two SSM parameters with the AWS role (same commands as the smoke job) and pass `-var="console_token=..." -var="ingest_hmac_secret=..."`; the values are masked with `::add-mask::`. PR plans for `infra/azure` must succeed (the PR job already assumes the AWS role). Outputs of `infra/azure`: `forwarder_url` (sensitive - contains the key), `notifications_app_name`, `action_group_id`, `alert_rule_names`.
4. Smoke: `scripts/chaos_probe.py` is reused: the deploy workflow's `chaos_probe` choice gains `notifications-429` (`--service customer-notifications --mode provider-429 --expect-alert Provider429`, timeout raised to 12 minutes for Azure Monitor's evaluation latency - make the timeout a `--timeout` flag with the current default).
5. Terraform gates on `infra/azure` (fmt, validate, tflint, checkov 0 failed - skips only with inline reasons, e.g. storage account key access needed by Y1 Functions).
6. Docs and diagrams: `docs/c4/workspace.dsl` - `azureEstate` gets `appInsights` (container, technology "Application Insights + Log Analytics") if missing and the relationships `notifications -> triage.api "GET /chaos (bearer)"`, `notifications -> appInsights "custom metrics"`, `monitor -> forwarder "action group webhook (common alert schema)"`, `forwarder -> triage.ingest "HTTPS + HMAC"`; regenerate. `infra/README.md`: "What infra/azure deploys" (with the ~3-minute first-warm note and the function-key note), the chaos cookbook entry for `customer-notifications` (`provider-429` -> `Provider429` rule -> verdict in 5-7 min; `backlog` -> `Backlog`), the plaintext-app-settings trade-off (Key Vault references = M9). `docs/DESIGN.md` section 3: customer-notifications marked deployed by M5; README roadmap row M5 updated to "deployed" (the live probe is recorded on the PR).
