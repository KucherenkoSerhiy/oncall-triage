# Spec: M4 - the AWS bank estate: payments, ledger, auth with switchable faults, CloudWatch alarms into the triage spine, `bankops chaos`

Builds on M2 (spine: SNS `alarms` topic already subscribed to `ingest`; the `cloudwatch` adapter expects the SNS alarm message with `AlarmName`, `AlarmDescription` containing `service=<name>`, `NewStateValue`, `NewStateReason`, `Trigger`), M2b (`services/console_api`, `cli/bankops`), M2c/M3b (`infra/aws`: Lambdas under the workload permissions boundary - which allows DynamoDB, SQS, SNS publish, logs, `cloudwatch:PutMetricData`, `ssm:GetParameter` but NOT `ssm:PutParameter`). Repository conventions unchanged; all offline gates must pass (ruff / ruff format / mypy with new packages listed / pytest; `terraform fmt`, `init -backend=false` + `validate`, `tflint`, `checkov` with inline reasons for any skip). New Python dependencies: none (boto3 only). Keep the always-free budget: at most 4 new custom metrics and at most 6 new alarms.

## Requirements

1. Fault control plane. A DynamoDB table `bank-faults` (hash `service`; provisioned 1/1) holds one item per service: `{service, mode, until (epoch seconds), set_at, set_by}`. `services/console_api` gains routes `GET /chaos` (list current faults with `active` = `until > now`), `POST /chaos/{service}` (JSON `{"mode": "<mode>", "minutes": 5}`, validates the service is one of `payments|ledger|auth` and the mode is valid for it, writes the item, 201) and `DELETE /chaos/{service}` (clears, 204); bearer-token protected like the rest; its IAM policy gains `dynamodb:GetItem/PutItem/DeleteItem/Scan` on that table only. `docs/api.md` documents the routes.
2. `bank/aws/common.py`: `current_fault(service) -> str | None` (reads the item, returns `mode` only while `until` is in the future, else `None`; tolerates a missing table item), `emit_metric(name, value, service)` (`cloudwatch:PutMetricData` in namespace `Nordwind/Bank` with dimension `service`), and `fail(message)` raising `BankFault(message)`. Table name from `BANK_FAULTS_TABLE`.
3. `bank/aws/payments/handler.py` (EventBridge schedule, every minute): normal path processes a batch of 5 synthetic authorisations and sends 5 messages `{"txn_id", "amount", "currency": "EUR"}` to the SQS queue `LEDGER_QUEUE_URL`, then returns `{"authorised": 5}`. Faults: `errors` -> raise `BankFault("upstream issuer returned 503")` (drives the Lambda `Errors` metric); `latency` -> sleep 2.5 s before succeeding (drives `Duration`); `pool` -> emit metric `PoolExhausted` = 1 and raise `BankFault("connection pool exhausted while authorizing payment")`.
4. `bank/aws/ledger/handler.py` (SQS event source on the ledger queue, batch 5, `ReportBatchItemFailures`): normal path "posts" each message and returns no failures. Faults: `lag` -> return every record as a batch failure without processing (messages stay in the queue and `ApproximateAgeOfOldestMessage` grows); `reconciliation-mismatch` -> emit metric `ReconciliationMismatch` = 1 once per invocation and process normally.
5. `bank/aws/auth/handler.py` (EventBridge schedule, every minute): normal path "issues" 20 tokens and returns `{"issued": 20}`. Faults: `jwks-rotation` -> emit metric `AuthFailures` = 20 and raise `BankFault("JWT signature verification failed: unknown key id kid-77")`; `lockouts` -> emit metric `AccountLockouts` = 7 and succeed.
6. Terraform, `infra/aws/bank.tf`: the faults table; the ledger SQS queue (+ DLQ, `maxReceiveCount` 5, visibility 60 s); three Lambdas (python3.12, arm64, 128 MB, 10 s; zip built from `bank/aws/` with a second `archive_file`), each with its own role under the permissions boundary and a policy scoped to exactly what it touches (faults table read; payments: send to the ledger queue; ledger: consume the ledger queue; all: `cloudwatch:PutMetricData` with a `cloudwatch:namespace` = `Nordwind/Bank` condition); log groups with 14-day retention; EventBridge rules `rate(1 minute)` for payments and auth with the matching `aws_lambda_permission`; the ledger event source mapping. Tags `c4_container` = `payments` / `ledger` / `auth` / `faults`.
7. Terraform, `infra/aws/alarms.tf`: six CloudWatch alarms, all with `alarm_actions = [aws_sns_topic.alarms.arn]`, `treat_missing_data = "notBreaching"`, `AlarmDescription` starting with `service=<name>` and a human sentence, alarm names `nordwind-triage-demo-<service>-<Signal>-Sev<N>`: payments `Errors` sum >= 3 over 5 min (Sev2); payments `Duration` p99 > 2000 ms over 5 min (Sev3); payments `PoolExhausted` sum >= 1 over 1 min (Sev3, description contains the exact phrase `connection pool exhausted` so the seeded known issue matches); ledger `ApproximateAgeOfOldestMessage` max > 300 s over 5 min (Sev2); ledger `ReconciliationMismatch` sum >= 1 (Sev1); auth `AuthFailures` sum >= 15 over 5 min (Sev2). Output `alarm_names`.
8. `cli/bankops`: `chaos <service> --mode <mode> [--minutes 5]` (POST), `chaos <service> --clear` (DELETE), `chaos --status` (GET, table of service / mode / minutes remaining). Modes per service are validated client-side too, with a helpful error listing the valid ones.
9. Tests: `tests/bank/` (moto for DynamoDB, SQS, CloudWatch): `current_fault` expiry semantics; payments normal path sends 5 messages, `errors` raises, `latency` sleeps (monkeypatch `time.sleep`), `pool` emits the metric and raises with the known phrase; ledger normal / `lag` batch failures / mismatch metric; auth paths; console-api chaos routes (validation, 201/204/404); bankops chaos commands with the HTTP function monkeypatched. Terraform gates on `infra/aws`.
10. Docs and diagrams: `docs/c4/workspace.dsl` - `awsEstate` gains the `faults` table and the `ledger queue` containers and the relationships (payments -> ledger queue -> ledger; console API -> faults; all three -> alarm topic); regenerate exports. `infra/README.md` gets "What the AWS bank estate deploys" and a "Chaos cookbook" (the three demo commands and what alarm each produces, with expected time-to-verdict ~3-5 min). `docs/DESIGN.md` §3 table: mark the three AWS services as deployed by M4.

## Non-requirements

Kafka, Kubernetes, Azure, the customer-notifications service, the random-incident scheduler (M9), Slack/e-mail delivery, real payment logic, X-Ray, any live AWS call in tests.
