# Spec: M9d - environment-scoped OIDC subjects for PR plans on both clouds (retire the `pull_request` subject; remove the checkov CKV_AZURE_249 skip)

Slice 4 of 5 of `docs/specs/m9-hardening.md` (requirement 5). Builds on M1 (`infra/bootstrap/aws`: OIDC provider + deploy role whose trust policy accepts `repo:<owner>/<repo>:pull_request`, `:ref:refs/heads/master` and `:environment:demo` in both the classic and the immutable subject form; `infra/bootstrap/azure`: eight federated credentials mirroring those subjects; `#checkov:skip=CKV_AZURE_249` on the `pull_request` credential), `deploy.yml` (plan jobs run on `pull_request` with the shared role; apply jobs run in the `demo` environment). Repository conventions unchanged; Terraform gates on both bootstrap roots. **This slice changes the bootstrap roots, which only a human credential can apply** - the PR ships the code and the exact commands; the workflow switch (step 4) is merged only after the owner confirms both applies succeeded (a two-PR slice).

## Requirements

1. GitHub: a `plan` environment (no required reviewers, no secrets beyond what `vars` already provide) created **by Terraform** in `infra/bootstrap/github/` - a new tiny root using the `integrations/github` provider (token from `GITHUB_TOKEN` in the operator's shell; state in the same S3 bucket under `bootstrap/github.tfstate`) that manages the `plan` and `demo` environments and their protection rules (demo: required reviewer = the repo owner, wait timer 0; plan: none). Import the existing `demo` environment (`terraform import`) - document the command. If the `github` provider cannot manage the owner's reviewer for a personal repository, fall back to managing only the `plan` environment and say so in the README.
2. `infra/bootstrap/aws`: the deploy role's trust policy drops the `:pull_request` subjects and adds `:environment:plan` (classic + immutable forms), keeping `:ref:refs/heads/master` and `:environment:demo`; the `NeverEditOwnIdentity` deny stays. `infra/bootstrap/azure`: the `pull_request` federated credential is replaced by `environment:plan` (classic + immutable), so the `#checkov:skip=CKV_AZURE_249` line goes away and checkov passes on its own. Both roots: `terraform plan` output pasted into the PR by the owner (the PR template asks for it).
3. `infra/README.md` "Bootstrap" gains a "Rotating the PR subject to an environment (M9d)" procedure: the two human commands (`terraform -chdir=infra/bootstrap/aws apply` with a temporary IAM user key that is deleted afterwards - link the existing note; `terraform -chdir=infra/bootstrap/azure apply` after `az login`), the order (bootstrap first, then merge the workflow PR), and the rollback (re-add the `pull_request` subject).
4. Second PR (opened by the same slice, merged after the owner's confirmation): `deploy.yml` plan jobs declare `environment: plan` (so their OIDC token carries the `environment:plan` subject) and keep `pull_request` as the trigger; `estate-demo.yml` and `diagnose.yml` unchanged (they already run in `demo`). CI proves the subject works when the first PR plan after the merge passes `configure-aws-credentials` and `azure/login`.
5. ADR 0008 (delivery pipeline) amended: why the `pull_request` subject was acceptable for M1-M8 (public repo, plan-only permissions were never true - the role is the same as apply's, which is exactly why the subject should be narrower), what changes, and the residual risk (a PR from a fork never gets the token because environments require a branch of this repository).
6. Tests / gates: Terraform fmt / validate / tflint / checkov on the three bootstrap roots; `checkov` with the CKV_AZURE_249 skip removed must pass; a `tests/test_workflows.py` unit test parses the three workflow files and asserts every job that assumes a cloud role declares an environment (`plan` or `demo`).

## Non-requirements

Separate plan and apply roles with different permissions (a v2 item; noted in the ADR), OIDC for `estate-demo.yml`'s Azure side (it does not talk to Azure), GitHub Apps.
