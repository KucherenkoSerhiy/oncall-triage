# Spec: M9a - self-observability: CloudWatch dashboard, four ops alarms into an `ops` topic, SLO document + `slo-reporter` Lambda, `CapReached` alarm

Slice 1 of 5 of `docs/specs/m9-hardening.md` (requirements 1, the alarm half of 2, 8, 9). Builds on M2c/M3 (`infra/aws`: ingest / console-api / triage-worker Lambdas, the alerts queue + DLQ, the API Gateway, the `verdicts` and `alerts` tables, `services/triage_worker/cap.py` with its `cap#<date>` counter item), M4 (`bank.tf` patterns: EventBridge schedule + Lambda + scoped IAM under the workload boundary; `alarms.tf` naming), the `diagnose.yml` workflow (what an operator looks at by hand today - the dashboard replaces most of it). Repository conventions unchanged; all offline gates must pass (moto for the new Lambda; Terraform fmt / validate / tflint / checkov with inline reasons). Cost: CloudWatch dashboard (1 free), 4 alarms (10 free, 6 used by M4 -> stay inside 10 by using **composite-free metric math** where two signals can share an alarm, or accept ~$0.10/month per extra alarm and say so in `docs/DESIGN.md` section 8), one custom metric, one 128 MB Lambda once a day.

## Requirements

1. `infra/aws/observability.tf`: SNS topic `${local.name_prefix}-ops` (no KMS - same reasoning and checkov skip as the alarms topic, #47) with an e-mail subscription to `var.notification_email`; four `aws_cloudwatch_metric_alarm`s with `alarm_actions` and `ok_actions` to it, `treat_missing_data = "notBreaching"`, names `${local.name_prefix}-ops-<Signal>`: `IngestErrorRatio` (metric math: `errors / invocations > 0.05` over 5 min, 1 period), `WorkerErrors` (`Errors` sum >= 3 over 15 min), `AlertsDlqDepth` (`ApproximateNumberOfMessagesVisible` on the DLQ >= 1, 1 min), `WorkerDurationP95` (`Duration` p95 > 60000 ms over 5 min). These alarms must **not** publish to the `alarms` topic (they would triage themselves): the `ops` topic is human-only.
2. `CapReached`: `services/triage_worker/handler.py` emits custom metric `Nordwind/Triage` `CapReached` = 1 (dimension `estate=all`) when the daily cap short-circuits a verdict (it already writes the "Daily LLM cap reached" summary); the worker's IAM policy gains `cloudwatch:PutMetricData` limited to that namespace (same condition pattern as the bank Lambdas); a fifth alarm `${local.name_prefix}-ops-CapReached` (sum >= 1 over 5 min) into the `ops` topic. Unit test: the cap path calls the metric emitter (injectable / monkeypatched boto client), the normal path does not.
3. `bank/ops/slo_reporter/handler.py` (new package `bank.ops`, listed in mypy/ruff config): EventBridge schedule `cron(15 0 * * ? *)` (daily 00:15 UTC), 128 MB, 60 s, reads yesterday's alerts by `received_at` prefix (query the `by_status` index for `triaged` items then filter by date - or add a GSI `by_day` if the scan would be unbounded; justify in a comment) and their verdicts, computes `latency_seconds = verdict.created_at - alert.received_at` per alert, and publishes custom metrics `Nordwind/Triage` `VerdictLatencyP95` (seconds, dimension `day=<YYYY-MM-DD>` NOT used - keep dimensions to `estate=all` so the metric has one time series), `AlertsTriaged` (count), `SloAttainment` (fraction of alerts with latency <= 300 s); logs one JSON line `{"day", "alerts", "p95_seconds", "attainment"}`. Own IAM role under the boundary: read on the two tables (+ index), `cloudwatch:PutMetricData` with the namespace condition, logs. Terraform in `observability.tf` (schedule, permission, role, log group 14 d).
4. `docs/slo.md`: the one SLO ("95 % of alerts receive a verdict within 5 minutes of arrival, measured daily from `received_at` to the verdict's `created_at`"), what counts (every estate; known-issue short-circuits count as verdicts; cap short-circuits count as **misses**), the error budget (30-day window, 5 % -> what that means in alerts per day at current volume), how it is measured (`slo-reporter` -> `SloAttainment`), and where it shows (dashboard widget). Link it from `docs/DESIGN.md` section 8 and the README "what a reviewer should look at" list.
5. `aws_cloudwatch_dashboard` `${local.name_prefix}` with widgets (JSON built with `jsonencode`, no hand-written strings): ingest invocations/errors/p95; queue depth + DLQ depth + age of oldest message; worker invocations/errors/throttles/p95; API Gateway 4xx/5xx/latency; the bank estate's `Nordwind/Bank` metrics (PoolExhausted, ReconciliationMismatch, AuthFailures, AccountLockouts); `VerdictLatencyP95`, `SloAttainment` (with a horizontal annotation at 0.95) and `CapReached`; an alarm-status widget listing the five ops alarms. Output `dashboard_url` (console deep link for `eu-north-1`).
6. `diagnose.yml`: a first step prints the dashboard URL and the five ops alarm states (`describe-alarms --alarm-name-prefix ${PREFIX}-ops-`), so the runbook can say "open the dashboard, then run diagnose".
7. Tests: `tests/bank/ops/test_slo_reporter.py` with moto (two alerts with verdicts -> p95 / attainment / count assertions, an alert without a verdict is ignored, an empty day publishes `AlertsTriaged=0` and no p95), `tests/triage_worker` cap-metric tests; Terraform gates on `infra/aws` (checkov: the ops topic skip with the same reason as #47).
8. Docs and diagrams: `docs/c4/workspace.dsl` - the triage system gains `ops topic` and `slo-reporter` containers and a `dashboard` (technology "CloudWatch dashboard") with relationships `slo-reporter -> alerts/verdicts tables "reads yesterday"`, `slo-reporter -> dashboard "custom metrics"`, `ops alarms -> ops topic -> operator`; regenerate exports. `infra/README.md`: "Self-observability" section (what pages a human vs what feeds triage, the five alarms, the dashboard, the SLO), and the cost line. `docs/DESIGN.md` section 8 (cost model) updated with the alarm count and the ~$0.30/month delta if any alarm goes beyond the free 10. README roadmap row M9 mentions M9a done.
