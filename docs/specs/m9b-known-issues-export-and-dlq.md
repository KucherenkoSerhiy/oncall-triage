# Spec: M9b - known-issues weekly export to S3 and `bankops known-issues import`; `bankops replay-dlq`

Slice 2 of 5 of `docs/specs/m9-hardening.md` (requirement 3 and the `replay-dlq` half of requirement 2). Builds on M2b/M3 (`services/console_api` known-issues routes and the `known-issues` table; `oncall_triage/stores.py`), M4 (`bank.tf` patterns for a scheduled Lambda under the workload boundary), M9a (`bank/ops` package and `observability.tf` exist - add to them rather than creating parallel homes), `cli/bankops` (argparse subcommands, `client.request`, config with `api` and token). Repository conventions unchanged; all offline gates must pass (moto for S3/DynamoDB/SQS). Cost: one private S3 bucket with a 30-day lifecycle (cents), one 128 MB Lambda once a week.

## Requirements

1. `infra/aws/observability.tf` (or a new `backups.tf` if the file grows past ~400 lines): private S3 bucket `${local.name_prefix}-known-issues-<account id>` (versioning off, SSE-S3, public access block, lifecycle: expire after 30 days, `abort_incomplete_multipart_upload` 7 days; checkov skips with reasons for access logging / cross-region replication / KMS as in the other buckets), Lambda `bank/ops/known_issues_export/handler.py` (EventBridge `cron(30 0 ? * MON *)`, 128 MB, 60 s) that scans the known-issues table and writes `known-issues-<YYYY-MM-DD>.json` (`{"exported_at", "count", "items": [...]}`, sorted by service then issue_id, Decimals rendered as numbers) to the bucket; IAM: scan on the table, `s3:PutObject` on `arn:.../known-issues-*.json` only, logs; log line `{"event": "known-issues-export", "count", "key"}`. Output `known_issues_bucket`.
2. `bankops known-issues export-now` is **not** added (the schedule is enough); instead `bankops known-issues import <file.json> [--dry-run]` reads an export file and re-teaches every item through the console API (`POST /known-issues`), skipping items whose `service` + `pattern` already exist (fetch the list first), printing `imported / skipped / failed` counts; exit 1 if any failed. `bankops known-issues list` already exists - keep it.
3. `bankops replay-dlq [--max 10] [--yes]`: moves up to `--max` messages from the alerts DLQ back to the alerts queue (`receive_message` with `MaxNumberOfMessages` <= 10 and a 30 s visibility timeout, `send_message` to the main queue preserving the body, then `delete_message` from the DLQ), prints one line per message (`alert_id` parsed from the body when present) and refuses to run without `--yes` after printing what it would do (`--dry-run` semantics without the flag). Queue URLs come from `bankops` config keys `alerts_queue_url` / `alerts_dlq_url` (new env vars `BANKOPS_ALERTS_QUEUE_URL` / `BANKOPS_ALERTS_DLQ_URL`, documented; `infra/aws` already outputs `alerts_queue_url` - add `alerts_dlq_url`). This command needs AWS credentials (it talks to SQS directly, not to the console API) - say so in `--help` and the README; the deploy role can run it from a workflow later.
4. `.github/workflows/diagnose.yml` gains an optional input `replay_dlq_max` (default `0`): when > 0, a final step runs `python -m cli.bankops replay-dlq --max <n> --yes` with the deploy role - the operator path for a poison-message incident without a laptop.
5. Tests: `tests/bank/ops/test_known_issues_export.py` (moto: table with 3 items -> object written with the expected key and sorted content; empty table -> `count 0` object still written), `tests/cli/bankops/` for `known-issues import` (dry-run prints and posts nothing; duplicates skipped; a 500 counts as failed and exits 1) and `replay-dlq` (moto SQS: 3 messages moved, DLQ empty afterwards, main queue has 3; without `--yes` nothing moves and the plan is printed; `--max 2` moves 2). Terraform gates.
6. Docs and diagrams: `docs/c4/workspace.dsl` - `known-issues bucket` container + `known-issues-export -> bucket` and `-> known-issues table` relationships; regenerate. `infra/README.md`: "Backups" (why a weekly JSON export is enough for a demo, how to restore with `bankops known-issues import`) and "Poison messages" (how `replay-dlq` and the `AlertsDlqDepth` alarm fit together). `docs/api.md` unchanged (no new routes). README roadmap row M9 mentions M9b.

## Non-requirements

Point-in-time recovery on DynamoDB (costs; documented as the production answer in `infra/README.md`), cross-account backups, encryption with a CMK, the other M9 slices.
