# Spec: M7 - the Kafka backbone: Strimzi (KRaft) + topics + SCRAM users, producers/consumers across the three Kubernetes services, `alerts-bridge` + `kafka-relay` (route A), kafka-exporter + lag rules, scenarios for both routes

Builds on M6 (`bank/k8s/*` services, `deploy/helm/nordwind-bank`, kube-prometheus-stack values, `task estate-up`, `estate-demo.yml`, `scripts/estate_scenarios.py`), M2 (`services/ingest/adapters/alertmanager.py`: a receiver name containing `kafka` marks route A; ingest verifies HMAC headers `X-Nordwind-Timestamp` / `X-Nordwind-Signature`), M5 (`bank/azure/_shared/hmac_sign.py` sign-only helper with the shared test vector - copy the same pattern into `bank/k8s/_shared/hmac_sign.py`; do not import `services.ingest` from images). `docs/DESIGN.md` section 4.4 describes both routes. Repository conventions unchanged; all offline gates must pass. New Python dependency: `confluent-kafka` (or `aiokafka` - pick one and use it everywhere). Contract tests use `testcontainers[kafka]` with the Redpanda image and are skipped when Docker is unavailable (CI has Docker). Nothing here costs money.

## Requirements

1. Strimzi: `deploy/helm/values/strimzi.yaml` for the upstream `strimzi-kafka-operator` chart (pinned), installed into `kafka` by `task estate-up` after kube-prometheus-stack. `deploy/helm/nordwind-bank/templates/kafka/` (all behind `kafka.enabled`, default `true` from M7 on): a `Kafka` + `KafkaNodePool` in KRaft mode (1 node, dual role, ephemeral storage, 512 Mi memory limit, listener `tls` 9093 with SCRAM-SHA-512), `KafkaTopic`s `card.authorized`, `fraud.scored`, `alerts.raw` (1 partition, 1 replica, 24 h retention), `KafkaUser`s `cards-authorization` (write card.authorized), `fraud-scoring` (read card.authorized, write fraud.scored, group `fraud-scoring`), `open-banking-api` (read fraud.scored, group `open-banking-api`), `alerts-bridge` (write alerts.raw), `kafka-relay` (read alerts.raw, group `kafka-relay`) with `simple` authorization ACLs scoped exactly to that, and `metricsConfig` + a `PodMonitor` so Prometheus scrapes the broker. Strimzi's own `kafka-exporter` is enabled on the `Kafka` resource (consumer-group lag metrics `kafka_consumergroup_lag`).
2. Service wiring: cards-authorization produces one `card.authorized` JSON event per `/work` tick; fraud-scoring consumes it, scores, produces `fraud.scored`; open-banking-api consumes `fraud.scored` and counts it (`openbanking_events_consumed_total`). Credentials from the Strimzi-generated user Secrets (mounted; `KAFKA_BOOTSTRAP`, `KAFKA_USER`, password file, cluster CA cert). Fault `lag` on fraud-scoring now works: the consumer stops polling (stays alive and healthy) so `kafka_consumergroup_lag{consumergroup="fraud-scoring"}` grows. Fault `broker-down` is a chaos action, not a service mode: `task chaos-k8s -- kafka broker-down` scales the Strimzi node pool to 0 replicas (annotates the pool with `strimzi.io/manual-rolling-update` is NOT the way - use `kubectl scale kafkanodepool`), `clear` scales back to 1.
3. `bank/k8s/alerts_bridge/`: HTTP server (8080, `/healthz`, `/metrics`) receiving Alertmanager webhooks on `/alertmanager`, producing one message per alert to `alerts.raw` with key = the alert fingerprint and value = the raw Alertmanager alert plus `{"receiver": "route-a-kafka", "bridge_ts": ...}`; counters `bridge_alerts_produced_total`, `bridge_produce_errors_total`. Deployed by the chart with its own ServiceMonitor.
4. `bank/k8s/kafka_relay/`: consumer of `alerts.raw` (group `kafka-relay`, manual commit after a successful POST) that wraps each message as an Alertmanager-shaped payload `{"receiver": "route-a-kafka", "alerts": [alert]}` and POSTs it to `INGEST_URL` with HMAC headers (`INGEST_HMAC_SECRET` from a Kubernetes Secret created by `task estate-up` from the SSM value, `--set-file` / `kubectl create secret`); on non-2xx it does not commit and retries with backoff (max 5, then commits and counts `relay_dropped_total`). Metrics `relay_posted_total`, `relay_failures_total`, `relay_dropped_total`, gauge `relay_last_success_timestamp_seconds`. Deployed by the chart, 1 replica.
5. Alertmanager routing (values in `kube-prometheus-stack.yaml`): default receiver `route-a-kafka` = webhook to `http://nordwind-bank-alerts-bridge.bank.svc:8080/alertmanager`; a first-match route sending `alertname=~"KafkaBrokerDown|KafkaRelayLag|AlertsBridgeDown"` to `route-b-forwarder` (M6 receiver); `continue: false`. New PrometheusRules in the chart: `KafkaBrokerDown` (`kafka_server_replicamanager_leadercount` absent or `up{job=~".*kafka.*"} == 0` for 1 m, critical, `service=kafka`), `KafkaConsumerLag` (`kafka_consumergroup_lag > 50` for 2 m, high, `service` = the consumer group), `KafkaRelayLag` (`kafka_consumergroup_lag{consumergroup="kafka-relay"} > 20` for 2 m or `time() - relay_last_success_timestamp_seconds > 300`, high, `service=kafka-relay`), `AlertsBridgeDown` (`up{job=~".*alerts-bridge.*"} == 0` for 1 m, critical, `service=alerts-bridge`).
6. `scripts/estate_scenarios.py` gains `--scenario fraud-lag` (set `lag`, wait for `KafkaConsumerLag` firing, wait for a verdict on `service=fraud-scoring` whose labels show `route=A`) and `--scenario broker-down` (scale to 0, wait for `KafkaBrokerDown`, wait for a verdict on `service=kafka` whose labels show `route=B`, then clear and wait for the broker pod to be Ready again). `estate-demo.yml` runs `cards-timeouts`, `fraud-lag`, `broker-down` in that order (total budget 25 min, raise the job timeout to 35) and uploads kafka-relay and alerts-bridge logs too. The README demo script quotes the two verdicts: one arrived over Kafka, the one about Kafka did not.
7. `task estate-up` order: kind, kube-prometheus-stack, strimzi operator, wait for the operator, `nordwind-bank` (CRs included), wait for `Kafka` `Ready` condition (10-min budget), then services. `task estate-status` also prints topics and consumer-group lag (`kubectl exec` into the broker with `kafka-consumer-groups.sh`).
8. `ci.yml`: `helm` job renders with `kafka.enabled=true` and `false` (kubeconform needs the Strimzi CRD schemas: use `-schema-location` with the datreeio CRDs-catalog URL, pinned); contract tests job runs the Redpanda-backed tests.
9. Tests: `tests/bank/k8s/` - bridge (webhook -> produced message shape and key; producer monkeypatched), relay (consume -> POST with verifiable HMAC; retry/backoff and drop after 5; commit only after 2xx), the `lag` fault on fraud-scoring (consumer stops polling, liveness stays true), scenario polling for the two new scenarios; contract tests under `tests/contract/` (Redpanda via testcontainers): bridge produces and relay consumes the same message end to end against a real broker, fraud-scoring consumes a real `card.authorized` and produces `fraud.scored`.
10. Docs and diagrams: `docs/c4/workspace.dsl` - `kubernetesEstate` gains `kafka` (Strimzi), `alerts-bridge`, `kafka-relay`, `kafka-exporter`; relationships for both routes (`kafka-relay -> triage.ingest "route A"`, `alertmanager -> forwarder "route B"`); dynamic view "an alert travels over Kafka"; regenerate. `docs/runbooks/kubernetes-estate.md` gains the Kafka section (topics, users, how to tail a topic, the two routes, `broker-down` recovery), ADR 0015 "Route A relay instead of a public Kafka endpoint" (context: kind has no public endpoint; AKS/MSK alternatives and cost). `docs/DESIGN.md` section 3: `lag`, `broker-down` marked live; README roadmap row M7.

## Non-requirements

AKS, MSK, Kafka Connect, Schema Registry, Kafka TLS client certs (SCRAM over the TLS listener is enough), multi-broker, Grafana dashboards, exactly-once semantics.
