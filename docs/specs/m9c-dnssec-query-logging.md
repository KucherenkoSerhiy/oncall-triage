# Spec: M9c - Route 53 DNSSEC for the delegated zone (KMS key, KSK, DS record at Cloudflare) and query logging

Slice 3 of 5 of `docs/specs/m9-hardening.md` (requirement 4). Builds on M2c (`infra/aws`: `aws_route53_zone.triage` for `triage.serhiykucherenko.dev`, `dns_delegation.tf` with the Cloudflare provider 5.x managing the NS records at the parent `serhiykucherenko.dev`, the `us-east-1` provider alias used for the CloudFront certificate). Repository conventions unchanged; Terraform gates on `infra/aws` (fmt / validate / tflint / checkov). Cost: one asymmetric KMS key (~$1/month) - the one deliberate increase in the whole M9, called out in `docs/DESIGN.md` section 8 and the README cost table.

## Requirements

1. `infra/aws/dnssec.tf`: `aws_kms_key` in `us-east-1` (Route 53 requirement) with `customer_master_key_spec = "ECC_NIST_P256"`, `key_usage = "SIGN_VERIFY"`, a key policy that lets `dnssec-route53.amazonaws.com` `kms:DescribeKey`, `kms:GetPublicKey`, `kms:Sign` (with `aws:SourceAccount` / `aws:SourceArn` conditions on the hosted zone) and `kms:CreateGrant` (grant-for-AWS-resource condition), plus the account root as admin; `aws_kms_alias` `alias/${local.name_prefix}-dnssec`; `aws_route53_key_signing_key` (name `${local.name_prefix}-ksk`, status ACTIVE); `aws_route53_hosted_zone_dnssec` depending on the KSK. Tags `c4_container = "dns"`.
2. Chain of trust at the parent: `cloudflare_dns_record` of type `DS` for `triage` in the `serhiykucherenko.dev` zone built from the KSK's attributes (`key_tag`, `signing_algorithm_type`, `digest_algorithm_type`, `digest_value`), TTL 3600, `depends_on` the hosted-zone DNSSEC resource. Document the ordering in the resource comment: zone signing must be enabled and propagated before the DS goes live, and the DS must be removed **before** disabling signing (the destroy order Terraform derives from `depends_on` gives exactly that; say so).
3. Query logging: `aws_cloudwatch_log_group` `/aws/route53/${local.name_prefix}` in `us-east-1` (7-day retention, `c4_container = "dns"`), the resource policy that lets `route53.amazonaws.com` write to it (`aws_cloudwatch_log_resource_policy`, scoped to that log group ARN), and `aws_route53_query_log` on the zone.
4. Outputs: `dnssec_ds_record` (the four DS fields as one string) and `dns_query_log_group`.
5. Verification script `scripts/dns_check.py` (stdlib + `subprocess` to `dig`, skipped/reported when `dig` is missing): prints whether `dig +dnssec triage.serhiykucherenko.dev NS` returns the `ad` flag and RRSIG records, whether the DS at the parent matches the zone's DNSKEY (via `dig DS` / `dig DNSKEY`), and the API/console hostnames still resolve; exit 1 on a mismatch. `task dns-check`. The deploy workflow's smoke job runs it in a non-fatal step (`continue-on-error: true` for the first week after the DS is published - DNSSEC validation depends on resolver caches; documented) and prints the result.
6. Docs and diagrams: `docs/c4/workspace.dsl` - the `dns` container (Route 53 zone) gains the description "DNSSEC-signed; query logs" and the deployment view shows the KMS key in us-east-1; regenerate. `infra/README.md`: "DNSSEC" (what is signed, the DS at Cloudflare, how to verify, the rollback order, the ~$1/month) and "DNS query logs" (where, retention, how to read them with Logs Insights). `docs/DESIGN.md` section 8 cost line; ADR 0009 (custom domain) amended with the DNSSEC decision; README roadmap row M9 mentions M9c.

## Non-requirements

Signing the parent zone at Cloudflare (Cloudflare signs `serhiykucherenko.dev` itself if the owner enables it - note the prerequisite in the README: the chain of trust only validates end-to-end when the parent is signed too), CAA records, DNS failover, multi-region.
