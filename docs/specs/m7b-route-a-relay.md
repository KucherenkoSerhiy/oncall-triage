# Spec: M7b - route A: `alerts-bridge` + `kafka-relay`, Alertmanager routing (A by default, B for Kafka's own alerts), Kafka alert rules, `fraud-lag` and `broker-down` scenarios, ADR 0015, C4 for the whole Kubernetes estate

Slice 2 of 2 of `docs/specs/m7-kafka-backbone.md`. Builds on M7a (Strimzi in the chart, `bank/k8s/_shared/kafka.py`, `KafkaUser`s `alerts-bridge` / `kafka-relay` and topic `alerts.raw` already exist, `chaos_k8s.py kafka broker-down`, kafka-exporter metrics), M6b (`scripts/estate_scenarios.py`, `estate-demo.yml`, the runbook), M5a (`bank/azure/_shared/hmac_sign.py` pattern - copy the same signer into `bank/k8s/_shared/hmac_sign.py` with the shared test vector; never import `services.*` from images), M2 (`services/ingest/adapters/alertmanager.py`: a receiver name containing `kafka` marks route A; label `service`; HMAC headers). Repository conventions unchanged; all offline gates, the `helm` job and the `contract` job must pass. Nothing here costs money.

## Requirements

1. `bank/k8s/alerts_bridge/`: HTTP server (8080; `/healthz`, `/metrics`, `POST /alertmanager`) that accepts an Alertmanager webhook payload and produces one message per alert to `alerts.raw`: key = the alert `fingerprint`, value = the alert object plus `{"receiver": "route-a-kafka", "bridge_ts": <iso>}`; answers 202 after all messages are flushed, 500 if any produce fails. Metrics `bridge_alerts_produced_total`, `bridge_produce_errors_total`. Uses `_shared/kafka.py` `make_producer` with the `alerts-bridge` credentials. Dockerfile like the other services; a Deployment + Service + ServiceMonitor in the chart (1 replica), only when `kafka.enabled`.
2. `bank/k8s/kafka_relay/`: consumer of `alerts.raw` (group `kafka-relay`, `enable.auto.commit=false`) that wraps each message as `{"receiver": "route-a-kafka", "status": "firing", "alerts": [<alert>]}` (an Alertmanager-shaped payload so the M2 adapter needs no change), signs it with `_shared/hmac_sign.py` (`X-Nordwind-Timestamp`, `X-Nordwind-Signature`) and POSTs to `INGEST_URL`; commits only after a 2xx; on non-2xx or network error retries with exponential backoff (1, 2, 4, 8, 16 s), then commits and counts `relay_dropped_total` so one bad message cannot block the partition. Metrics `relay_posted_total`, `relay_failures_total`, `relay_dropped_total`, gauge `relay_last_success_timestamp_seconds`, gauge `relay_inflight`. `INGEST_HMAC_SECRET` comes from a Kubernetes Secret `nordwind-ingest` that `task estate-up` creates from the SSM parameter (`aws ssm get-parameter --with-decryption --name /nordwind-triage/demo/ingest-hmac-secret`, documented; in `estate-demo.yml` it is read with the AWS role exactly as the smoke job does) - the chart references the Secret by name and never contains the value. Dockerfile, Deployment (1 replica) + Service + ServiceMonitor, only when `kafka.enabled`.
3. Alertmanager routing (`deploy/helm/values/kube-prometheus-stack.yaml`, still rendered by `scripts/render_alertmanager_values.py`): default receiver `route-a-kafka` = webhook to `http://nordwind-bank-alerts-bridge.bank.svc:8080/alertmanager` (`send_resolved: true`); a first-match child route with `matchers: ['alertname =~ "KafkaBrokerDown|KafkaRelayLag|AlertsBridgeDown|KafkaRelayDown"']` to `route-b-forwarder` (the M6a receiver), `continue: false`; `group_by: ['alertname', 'service']`, `group_wait: 10s`, `group_interval: 30s`, `repeat_interval: 1h`. When `kafka.enabled=false` the renderer must emit the M6 routing (everything to route B) - add a `--kafka/--no-kafka` flag and test both.
4. New PrometheusRules in the chart (labels `service`, `severity`; annotations `summary`, `description`): `KafkaBrokerDown` (`absent(kafka_server_replicamanager_leadercount) or sum(up{job=~".*kafka.*"}) == 0` for 1m, critical, `service=kafka`), `KafkaConsumerLag` (`sum by (consumergroup) (kafka_consumergroup_lag) > 50` for 2m, high, `service` = the consumer group via the `consumergroup` label - use a `label_replace` so the alert carries `service`), `KafkaRelayLag` (`sum(kafka_consumergroup_lag{consumergroup="kafka-relay"}) > 20 or time() - max(relay_last_success_timestamp_seconds) > 300` for 2m, high, `service=kafka-relay`), `AlertsBridgeDown` (`up{job=~".*alerts-bridge.*"} == 0` for 1m, critical, `service=alerts-bridge`), `KafkaRelayDown` (`up{job=~".*kafka-relay.*"} == 0` for 1m, critical, `service=kafka-relay`).
5. Scenarios in `scripts/estate_scenarios.py`: `fraud-lag` = set `lag` on fraud-scoring, wait for `KafkaConsumerLag` firing in Alertmanager (budget 8 min), wait for a verdict on the console API for `service=fraud-scoring` whose alert `labels.route == "A"` (budget 10 min), clear. `broker-down` = `chaos_k8s.py kafka broker-down`, wait for `KafkaBrokerDown` firing, wait for a verdict for `service=kafka` with `labels.route == "B"`, then `kafka clear` and wait for the broker pod Ready again (budget 5 min). Output for both must print the route the verdict took. `estate-demo.yml` runs `cards-timeouts`, `fraud-lag`, `broker-down` in that order (job timeout 40 min) and also uploads `kafka-relay` / `alerts-bridge` logs and `kubectl get kafka,kafkanodepool,kafkatopic,kafkauser -n bank -o yaml`.
6. Tests: `tests/bank/k8s/` for the bridge (webhook -> produced messages: key = fingerprint, value shape, 202 / 500; producer faked), the relay (consume -> POST body is Alertmanager-shaped and the headers verify with `services.ingest.hmac_auth.verify` in the test; commit only after 2xx; backoff sequence; drop after the last retry increments `relay_dropped_total`), the shared signer vector, the renderer's `--kafka/--no-kafka` routing (the Kafka alert names go to route B, everything else to A), the two new scenarios with kubectl + HTTP monkeypatched (happy path, rule never fires, wrong route in the verdict fails). `tests/contract/`: bridge produces to Redpanda and the relay consumes and POSTs to a local HTTP stub that verifies the HMAC; a failing stub (500 then 200) shows retry-then-commit.
7. Docs and diagrams: `docs/c4/workspace.dsl` - `kubernetesEstate` gains `kafka` (Strimzi, KRaft), `kafka-exporter`, `alerts-bridge`, `kafka-relay`; relationships `alertmanager -> alerts-bridge "route A webhook"`, `alerts-bridge -> kafka "produce alerts.raw"`, `kafka-relay -> kafka "consume alerts.raw"`, `kafka-relay -> triage.ingest "HTTPS + HMAC (route A)"`, `alertmanager -> forwarder "route B (Kafka's own alerts)"`; two dynamic views "an alert travels over Kafka (route A)" and "the alert about Kafka takes route B"; the `kind` deployment environment gains the Kafka pods; regenerate. ADR 0015 "Route A relay instead of a public Kafka endpoint" (context: kind has no public endpoint; alternatives AKS + private link / MSK and their cost; consequence: the relay is the one component that knows the HMAC secret inside the cluster). `docs/runbooks/kubernetes-estate.md`: the two routes, how to prove which route a verdict took (`labels.route` on the console), `broker-down` recovery. `docs/DESIGN.md` section 4.4 cross-checked; README roadmap row M7 + the demo script paragraph ("one verdict arrived over Kafka; the one about Kafka did not").

## Non-requirements

AKS, MSK, Kafka Connect, Schema Registry, exactly-once, multi-broker, Grafana.
