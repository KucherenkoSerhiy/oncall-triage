# Spec: M5a - Azure Function apps: customer-notifications (timer + chaos poll) and alert-forwarder (HMAC), shared signer, tests

Slice 1 of 2 of `docs/specs/m5-azure-estate.md` (M5b = Terraform + deploy.yml). Builds on M2 (`services/ingest/hmac_auth.py` `sign(secret: bytes, timestamp: str, body: bytes) -> str` and `verify`; the `azure-monitor` and `alertmanager` adapters), M2b/M4 (`services/console_api` chaos routes: `VALID_MODES`-style validation lives in `cli/bankops/commands.py` and in the console API handler - find the single source of truth the M4 code uses and extend it), and the repository conventions (ruff / ruff format / mypy with new packages listed in `pyproject.toml` / pytest; no live network in tests). New Python dependency for the function apps only: `azure-functions` (add it to each app's `requirements.txt`, and to the dev dependency group so tests can import `azure.functions`). Nothing here deploys anything.

## Requirements

1. `bank/azure/customer_notifications/` - an Azure Functions app in the Python v2 programming model: `function_app.py` (module-level `app = func.FunctionApp()`), `host.json` (version 2.0, Application Insights sampling settings block present), `requirements.txt`. One timer trigger `send_batch` with schedule `0 * * * * *` (every minute). The logic lives in importable, framework-free code (`notifications.py`) so tests never need the Functions host:
   - `ChaosClient(chaos_url, token, ttl_seconds=60, http=<injectable>)` with `current_mode(service="customer-notifications") -> str | None` that GETs `CHAOS_URL` with `Authorization: Bearer <CONSOLE_TOKEN>`, picks the entry for the service whose `active` is true, caches the answer for `ttl_seconds` (a failed poll returns the cached value, or `None`, and never raises).
   - `send_batch(mode, metrics)` "sends" 20 notifications and records metrics through a small `Metrics` protocol (`record(name, value)`), implemented for production by `AppInsightsMetrics` using the OpenTelemetry API (`opentelemetry.metrics.get_meter(...)`, counters/gauges; `azure-monitor-opentelemetry` in `requirements.txt` only, configured in `function_app.py` from `APPLICATIONINSIGHTS_CONNECTION_STRING` when present) and in tests by a recording fake. Normal: `notifications_sent = 20`. `provider-429`: `provider_429 = 20` then `raise ProviderError("SMS provider returned 429 Too Many Requests")`. `backlog`: `notifications_sent = 20`, `notifications_backlog = 150`, succeed.
   - Environment: `CHAOS_URL` (default `https://api.triage.serhiykucherenko.dev/chaos`), `CONSOLE_TOKEN`. Missing token -> the app logs a warning once and runs in normal mode.
2. `bank/azure/alert_forwarder/` - a second Function app: HTTP trigger `forward` (route `alerts`, `auth_level=FUNCTION`, POST) whose logic lives in `forwarder.py`:
   - `classify(payload) -> Literal["azure-monitor", "alertmanager"]`: `data.essentials` present -> `azure-monitor`; top-level `alerts` list present -> `alertmanager`; anything else -> `ValueError` (the trigger answers 400).
   - `forward(payload, ingest_url, secret, http=<injectable>) -> ForwardResult(status, source, alert_count)`: wraps as `{"source": <classified>, "payload": payload}`, signs with `bank/azure/_shared/hmac_sign.py` (headers `X-Nordwind-Timestamp`, `X-Nordwind-Signature`, `Content-Type: application/json`), POSTs to `INGEST_URL`; `alert_count` = `len(payload["alerts"])` for Alertmanager, 1 for Azure Monitor. The trigger returns 202 when ingest answered 2xx, else 502 with `{"ingest_status": <code>}`; it logs exactly one JSON line per request: `{"event": "forward", "source": ..., "ingest_status": ..., "alert_count": ...}`.
   - Environment: `INGEST_URL` (default `https://api.triage.serhiykucherenko.dev/alerts`), `INGEST_HMAC_SECRET`.
3. `bank/azure/_shared/hmac_sign.py` - `sign(secret: bytes, timestamp: str, body: bytes) -> str` and `signed_headers(secret, body, now=time.time) -> dict[str, str]`, a copy of the ingest algorithm with no import of `services.*` (the function apps deploy alone; each app's `requirements.txt` and zip contain only its own folder plus `_shared`, so `function_app.py` imports `_shared` via a relative-path-safe import - document how in a comment). `tests/bank/azure/test_hmac_sign.py` asserts that for a fixed secret, timestamp and body the shared `sign` equals `services.ingest.hmac_auth.sign` and that `services.ingest.hmac_auth.verify` accepts headers produced by `signed_headers`.
4. Control plane: `customer-notifications` becomes a valid chaos service with modes `provider-429` and `backlog` in the single source of truth used by the console API and `bankops chaos` (M4 introduced it - extend, do not duplicate). `bankops tail` prints an `estate` column (the alert's `estate` field, width 11) - adjust the existing column layout and its tests.
5. Tests, `tests/bank/azure/`: `ChaosClient` (mode picked from the active entry, TTL caching with an injected clock, poll failure falls back, no token -> normal), `send_batch` for all three modes with the recording metrics fake, `classify` on real-shaped fixtures (a common-alert-schema sample and an Alertmanager sample - put them under `tests/bank/azure/fixtures/`), `forward` happy path (assert the HMAC headers verify with `services.ingest.hmac_auth.verify` against the test secret, assert the wrapped body shape) and 502 path, the shared-sign vector; console API `POST /chaos/customer-notifications` accepts `provider-429` and rejects an unknown mode; `bankops chaos customer-notifications --mode backlog` and the `tail` estate column. Import `function_app` modules once in a test to prove they load under `azure.functions` (decorators are inert without the host).
6. Docs: `bank/azure/README.md` (what each app does, local run with `func start` for the curious, environment variables, why app settings are plaintext in v1 - M5b documents the Terraform side), `docs/api.md` chaos section lists the new service and modes, `docs/DESIGN.md` section 3: customer-notifications row says "M5a code / M5b deploy".

## Non-requirements

Terraform, deploy.yml, Azure Monitor alert rules, Key Vault, live calls of any kind, Kubernetes.
