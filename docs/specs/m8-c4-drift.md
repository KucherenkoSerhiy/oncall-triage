# Spec: M8 - the C4 pipeline closes the loop: `c4_drift.py` compares the model with Terraform tags and Helm labels, the kind deployment view, ADR completeness

Builds on M0/M1 (`docs/c4/workspace.dsl`, `scripts/c4_render.py`, the `c4` CI job that exports with `structurizr/structurizr` and fails on a stale `docs/c4/generated/`), M4/M5 (every Terraform resource carries a `c4_container` tag), M6/M7 (every Kubernetes workload carries the label `nordwind.dev/c4-container`). Repository conventions unchanged; all offline gates must pass. No cloud calls: drift is computed from the repository alone (`terraform show -json` of a plan is out of scope; parse HCL tags statically). New Python dependency: `python-hcl2`.

## Requirements

1. `scripts/c4_drift.py`: builds three sets and reports the differences.
   - Model set: container identifiers declared in `workspace.dsl` (parse the DSL with a small tolerant parser: `identifier = container "Name" ...` lines inside `softwareSystem` blocks, plus a `tags "c4:<id>"` convention is NOT required - use the identifier), grouped by software system.
   - Terraform set: every `c4_container` tag value under `infra/**/*.tf` (`tags = { c4_container = "..." }`, `merge(local.tags, { c4_container = "..." })`, and `default_tags` in the provider block - the last one applies to every resource of that root, so it counts as "root-level default" and is reported separately) with the resource address it came from.
   - Helm set: every `nordwind.dev/c4-container` label value in `helm template` output of `deploy/helm/nordwind-bank` rendered with `kafka.enabled=true` (skip the Helm set with a warning when `helm` is not on PATH).
   Output: a Markdown table (container, in model, in Terraform, in Helm, where) and exit 1 when (a) Terraform or Helm reference a container the model does not declare, or (b) a model container that is marked deployable (has the DSL tag `Deployable`) appears in neither Terraform nor Helm. An allow-list file `docs/c4/drift-allow.yaml` covers deliberate exceptions with a reason each (for example the console's static bucket).
2. Deliberate-failure test: `tests/test_c4_drift.py` builds a temp repo layout with one untagged resource and one unknown tag value and asserts exit 1 with both rows in the table; the happy path over the real repository is a test too (skipped if `helm` is missing).
3. CI: the `c4` job runs `python scripts/c4_drift.py --strict` after the export drift check; `task c4-drift` locally. The job summary (`$GITHUB_STEP_SUMMARY`) gets the table.
4. Model completeness: `workspace.dsl` gains the `Deployable` tag on every container that is a cloud resource or a Kubernetes workload; a `deploymentEnvironment "kind"` with the laptop and the GitHub Actions runner nodes (containerInstances for the six workloads, Prometheus, Alertmanager, Kafka); a dynamic view per route (route A over Kafka, route B over the forwarder); the `awsEstate` / `azureEstate` / `kubernetesEstate` container views verified against M4-M7. Regenerate; `docs/c4/generated/README.md` lists every view with one line of purpose.
5. ADRs: 0015 (route A relay, if M7 did not write it), 0016 "C4 drift as a merge gate" (why tags/labels are the join key, the allow-list, what it does not catch); the ADR index in `docs/adr/README.md` is regenerated by `scripts/c4_render.py` or a sibling `scripts/adr_index.py` with a CI check that it is current.
6. Docs: `docs/DESIGN.md` section 4 diagrams cross-checked against the generated C4 views (fix any container names that diverged since v2.1; bump to v2.2 with a changelog line). README roadmap row M8; `docs/c4/README.md` explains the loop: model -> export -> render -> drift, and how to add a container (declare in the DSL, tag the resource, run `task c4`).

## Non-requirements

Live-cloud drift (comparing the model with what is actually deployed), Structurizr Lite/on-prem UI, PlantUML, importing Terraform state.
