# Spec: M3b - ship the real triage worker: ECR, image build in the pipeline, image-based Lambda, Anthropic key

Builds on M3a (`services/triage_worker/Dockerfile`, the real handler) and M2c (`infra/aws/lambdas.tf` where `aws_lambda_function.triage_worker` is a zip-packaged function). Offline gates as in M2c: `terraform fmt -check`, `init -backend=false` + `validate`, `tflint`, `checkov` (inline reasons for any skip), plus `ruff`/`mypy`/`pytest` where Python changes. Provider ranges are already declared in `infra/aws/versions.tf`.

## Requirements

1. `infra/aws/ecr.tf`: `aws_ecr_repository` `${local.name_prefix}-triage-worker` (image tag immutability `IMMUTABLE`, scan on push, `AES256` encryption), lifecycle policy keeping the last 10 images, tag `c4_container = "worker"`. Output `worker_repository_url`.
2. Deploy role: no change (its `ecr:*` grant already covers push). Document in `infra/README.md` that the image is pushed by `deploy.yml` with the OIDC role.
3. `.github/workflows/deploy.yml`: a new job `image` (runs after `preflight`, before `plan` on pushes to the default branch and on `workflow_dispatch`; skipped on pull requests) that logs in to ECR with `aws-actions/amazon-ecr-login`, builds `services/triage_worker/Dockerfile` for `linux/arm64` with `docker buildx` (QEMU set up via `docker/setup-qemu-action`), tags it `<repo>:sha-<git sha>` and `<repo>:latest`, pushes both, and exports `worker_image_sha=sha-<git sha>` as a job output. `plan` and `apply` receive `-var="worker_image_sha=<value>"` where `<value>` is the `workflow_dispatch` input when given (rollback), else the `image` job output on pushes, else omitted (pull requests plan with the variable's default). On pull requests the plan must still succeed: the Lambda then points at the tag `var.worker_image_sha` = `latest` (documented default) so the plan is realistic; a fresh account with no image yet is handled by requirement 5.
4. `infra/aws/lambdas.tf`: `aws_lambda_function.triage_worker` becomes `package_type = "Image"` with `image_uri = "${aws_ecr_repository.triage_worker.repository_url}:${var.worker_image_sha}"`, `architectures = ["arm64"]`, memory 1024 MB, timeout 120 s, and the environment `ALERTS_TABLE`, `VERDICTS_TABLE`, `KNOWN_ISSUES_TABLE`, `ANTHROPIC_API_KEY` (from `data.aws_ssm_parameter.anthropic_api_key` - see 5), `TRIAGE_MODEL` (from `var.triage_model`, default `anthropic/claude-haiku-4-5-20251001`), `DAILY_ALERT_CAP` (from `var.daily_alert_cap`, default 500), `LOG_LEVEL`. Its role gains `dynamodb:Query` on the alerts table and its `by_status` index and `dynamodb:Query`/`PutItem` on the known-issues table (the tools need them), plus `dynamodb:UpdateItem` on the verdicts table (the daily-cap counter). Remove the zip-based worker definition and anything only it used; ingest and console-api stay zip-packaged.
5. Anthropic key: the SSM parameter `/${var.project}/${var.environment}/anthropic-api-key` is NOT created by Terraform (its value is a human secret); Terraform reads it with `data "aws_ssm_parameter"` and the README documents the one-time operator command `aws ssm put-parameter --name ... --type SecureString --value ... --overwrite`. `deploy.yml` gets a manual `workflow_dispatch` input `anthropic_api_key` (type string, optional) that, when provided, runs `aws ssm put-parameter` with the deploy role before `plan` - so the owner can set or rotate the key from the Actions UI without a local AWS credential; the value must never be echoed (mask with `::add-mask::`). If the parameter does not exist, `plan` must fail with a clear message from a `precondition` on the data source's consumer (`aws_lambda_function.triage_worker`) saying which command creates it.
6. First-deploy ordering: the `image` job pushes before `plan` runs, so `:sha-<sha>` exists when `apply` creates the function. Because the repository is created in the same apply, the `image` job must create the ECR repository if missing? No - avoid that race by splitting: the ECR repository moves to its own tiny root `infra/aws-ecr` (same backend bucket, key `aws-ecr/terraform.tfstate`) applied by `deploy.yml` in a job `ecr` that runs before `image`; `infra/aws` reads the repository URL with `data "aws_ecr_repository"`. Document the ordering in `infra/README.md` (`ecr` -> `image` -> `plan` -> `apply`).
7. Rollback: `workflow_dispatch` with `worker_image_sha` = an earlier `sha-<sha>` redeploys that image; the README gets a "Rollback" section with the exact command (`gh workflow run deploy.yml -f root=aws -f worker_image_sha=sha-<sha>`). ADR 0008 gains one sentence pointing at it.
8. Smoke probe update: `scripts/smoke.py` additionally asserts the verdict for the synthetic alert has `model` different from `stub` and `cap` and that `known` is `false` for service `smoke` (a fresh service has no known issues); a second probe fires an alert whose text matches the seeded known issue for `payments` (`connection pool exhausted`) and asserts `known` is `true` and `action` is `ack`. Unit tests updated accordingly.
9. C4: `docs/c4/workspace.dsl` deployment view gets an `ECR` deployment node holding a container instance of the worker image (or a note on the Lambda node) - keep it truthful; regenerate the exports. `docs/DESIGN.md` §4.3 runtime row and the M3 milestone row are updated to say the worker is an image-based Lambda built by the pipeline.

## Non-requirements

Provisioned concurrency, multi-region ECR replication, image signing (M9 candidate), Bedrock, any live model call in CI, changes to ingest or console-api packaging.
